# Documentation Standards

## Purpose

This skill defines how every AI agent should create, maintain, organize, and improve documentation across the company.

Its objective is to ensure documentation is:

- Clear
- Accurate
- Complete
- Consistent
- Maintainable
- Searchable
- Actionable
- Long-lasting

Documentation should preserve organizational knowledge—not merely describe software.

---

# When to Use

Use this skill whenever an agent is:

- Creating documentation
- Updating documentation
- Writing technical guides
- Documenting APIs
- Writing architecture documents
- Creating design documents
- Producing project reports
- Recording decisions
- Writing deployment guides
- Documenting incidents
- Creating knowledge articles

---

# Do Not Use

Do not use this skill for:

- Coding standards
- Security implementation
- Hiring decisions
- Product planning

Those responsibilities belong to their respective skills.

---

# Documentation Philosophy

Documentation is a company asset.

Good documentation reduces dependency on individuals.

Every document should help another engineer understand the system without needing additional explanation.

Documentation should remain useful months and years after it is written.

---

# Required Sections

Whenever applicable, documentation should include:

Purpose

Scope

Background

Architecture

Dependencies

Workflow

Configuration

Examples

Known Limitations

Related Documents

Revision History

Not every document requires every section, but important information should never be omitted.

---

# Writing Standards

Always:

- Use clear language.
- Keep formatting consistent.
- Use meaningful headings.
- Explain intent before implementation.
- Prefer diagrams when they improve understanding.
- Keep information organized logically.
- Use examples where appropriate.
- Define technical terms when needed.

Avoid:

- Ambiguous wording.
- Unexplained abbreviations.
- Personal opinions.
- Outdated information.
- Duplicate documentation.

---

# Technical Documentation

Technical documents should explain:

- System Purpose
- Architecture
- Components
- Dependencies
- Data Flow
- Interfaces
- Configuration
- Error Handling
- Deployment
- Monitoring
- Maintenance

Focus on understanding rather than code.

---

# API Documentation

Every public API should document:

- Purpose
- Endpoint
- Authentication
- Request Format
- Parameters
- Validation Rules
- Responses
- Error Codes
- Examples
- Version

API documentation should be sufficient for implementation without reading source code.

---

# Architecture Documentation

Architecture documents should explain:

- Business Problem
- Design Goals
- Major Components
- Responsibilities
- Communication Flow
- Technology Choices
- Scalability
- Security
- Trade-offs
- Future Improvements

Record why architectural decisions were made.

---

# Decision Documentation

Every significant decision should record:

- Problem
- Context
- Alternatives
- Selected Solution
- Reasoning
- Expected Benefits
- Risks
- Decision Owner
- Date
- Related Projects

Future agents should understand both the decision and its rationale.

---

# Knowledge Capture

Whenever work is completed, capture:

- Lessons Learned
- Best Practices
- Reusable Patterns
- Common Mistakes
- Architectural Improvements
- Performance Optimizations
- Operational Improvements

Documentation should continuously strengthen company knowledge.

---

# Version Control

Documentation should:

- Evolve with the project.
- Record major revisions.
- Remove obsolete information.
- Preserve historical context when necessary.
- Remain synchronized with implementation.

Outdated documentation is considered a defect.

---

# Maintenance Rules

Documentation should be updated whenever:

- Features change.
- Architecture changes.
- APIs change.
- Processes change.
- Security changes.
- Infrastructure changes.
- Lessons are learned.
- Incidents occur.

Never leave documentation inconsistent with reality.

---

# Documentation Review Checklist

Before publishing documentation verify:

- Is it accurate?
- Is it complete?
- Is it easy to understand?
- Is the structure logical?
- Are examples included where useful?
- Are related documents referenced?
- Is outdated information removed?
- Can another engineer work without additional explanation?

---

# Documentation Anti-Patterns

Never:

- Copy outdated documentation.
- Duplicate information unnecessarily.
- Leave placeholder sections.
- Ignore documentation after implementation.
- Hide assumptions.
- Mix unrelated topics.
- Write documentation only for the current project.

Documentation should benefit future projects as well.

# Final Directive

Documentation is the memory of the company.

Every document should enable future engineers and AI agents to understand systems, decisions, processes, and knowledge without relying on the original author.

The objective is not simply to document completed work.

The objective is to build a permanent organizational knowledge system that grows more valuable with every project the company completes.
